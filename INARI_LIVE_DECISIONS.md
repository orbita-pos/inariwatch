# Inari Live — Decision Log

Append-only. Each decision is dated, attributed to a session, and captures *what* was decided and *why* — so a future session can re-read the context without paging back through the master plan.

If a decision conflicts with a fixed constraint in `INARI_LIVE_HANDOFF.md` § *Spec recap*, the fixed constraint wins; the decision must be revised. Decisions that **clarify** spec ambiguities (without contradicting them) are valid.

## 2026-04-29 — Sesión 1

## 2026-04-29 — Sesión 2
Decision: Event bus uses `Arc<Mutex<VecDeque<DaemonEvent>>>` per subscriber + `flume::Sender<()>` notifier — NOT raw `flume` mpmc and NOT `tokio::sync::broadcast`.
Reason:   The spec said "flume-based broadcast channel". flume's mpmc primitive is *not* a broadcast — Receiver clones COMPETE for events, so each subscriber would only see a subset. tokio::sync::broadcast has the right semantics but couples sensors to a tokio runtime and complicates non-async sensor receive paths. The hand-rolled VecDeque + flume notifier gives true broadcast (each subscriber owns its queue), drop-oldest at the producer in O(1), and sync/async/timeout receive support without a tokio dependency.
Impact:   `daemon/bus.rs` is the canonical implementation. Sensors that need async receive call `Receiver::recv_async`; sync sensors call `Receiver::recv`/`recv_timeout`. Spec-compliant in semantics; flume is still in the dep tree (used for the notifier and as the spec-named primitive).

## 2026-04-29 — Sesión 3
Decision: Hand-rolled migration runner (`src/store/migrations.rs`, ~80 LoC) instead of refinery.
Reason:   Three migrations + no rollback story does not justify the dep cost. refinery 0.8 + rusqlite 0.31 also pulls feature-gating gymnastics around its async-postgres transitive defaults; hand-rolling is faster to audit, ships zero new transitive deps, and the SQL is `include_str!`-baked into the binary for byte-stability across builds.

Reason:   HANDOFF.md's Session 3 spec body said `FLOAT[1024]` but Session 6's spec body locks the embedding model as MiniLM-L6-v2, which emits 384-dim vectors (`fastembed-rs` ships it as the default). ## 2026-04-29 — Sesión 3
Decision: sqlite-vec is loaded via `rusqlite::ffi::sqlite3_auto_extension` registered exactly once at process start (`std::sync::Once` in `src/store/pool.rs`), NOT via per-acquire `Connection::load_extension` calls.
Reason:   This is the upstream sqlite-vec crate's documented pattern — the global auto-extension is invoked by SQLite on every newly-opened connection (including those produced inside r2d2_sqlite's `SqliteConnectionManager`), so all pooled connections get vec0 loaded with zero per-acquire FFI cost. Per-connection `load_extension` requires toggling `enable_load_extension` on each acquire and is strictly more work for the same effect. The `Once` keeps repeated `Store::open_at` calls (e.g. across tests in the same process) safe.
Impact:   `r2d2::CustomizeConnection::on_acquire` is responsible only for connection-local PRAGMAs (`foreign_keys`, `temp_store`, `busy_timeout`, `mmap_size`, plus a defensive `journal_mode=WAL` query). Tests `store_sqlite_vec_loaded` and `store_pool_connections` exercise both paths.

## 2026-04-29 — Sesión 4
Decision: `IpcError` is a typed enum with 8 variants (`Migration`, `Connection`, `ExtensionLoad`, `Io`, `Query`, `InvalidPath`, `RepoNotFound`, `Internal`) — NOT a stringly-typed error.
Reason:   The Session-4 spec called for "discriminate the 5 most actionable variants of `StoreError`". An enum with `#[serde(tag = "kind")]` lets the dock pattern-match in TS via the auto-generated tagged union and surface variant-specific UX (e.g. "DB is from a newer build — please update" only on `Migration`). Going through `String` would force the frontend to regex-parse error messages.
Impact:   `From<StoreError> for IpcError` discriminates the 5 spec-listed variants and collapses `PathResolution` into `Internal`. ts-rs generates `desktop/src/lib/types/IpcError.ts` as a tagged union; the frontend wrapper exposes `isIpcError(err)` as a type guard.

## 2026-04-29 — Sesión 4
Decision: Pick `ts-rs = "8"` over hand-rolled or `serde-reflection`. ts-rs's auto-generated `export_bindings_*` lib tests refresh the `.ts` files on every `cargo test --lib`.
Reason:   Track 5 will end with ~30 DTOs. Hand-rolling would diverge silently the first time a Rust struct gains a field. ts-rs piggybacks on existing `#[derive(Serialize)]` annotations with one extra `#[derive(TS)]` and `#[ts(export)]`; output lands in the directory the frontend imports from. ts-rs v8 emits one `export_bindings_<type>` test per `#[ts(export)]` annotation, so no manual entry-point test is needed — the bindings stay in sync with zero contributor friction.
Impact:   The four Session-4 DTOs (`DaemonStatusDto`, `RepoDto`, `LogEntryDto`, `IpcError`) land at `desktop/src/lib/types/*.ts`. Generated files are committed alongside the Rust source. CI can rely on `cargo test --lib` to fail if a contributor forgets to commit a regenerated binding.

## 2026-04-29 — Sesión 4
Decision: `started_at` ISO is computed once via `OnceLock` in `snapshot_to_dto`, then cached for the rest of the process lifetime.
Reason:   Without caching, `started_at = now() - uptime_secs` drifts whenever wall-clock advances faster than the heartbeat-driven `uptime_secs` — between heartbeats the difference would slide by up to 30 s. The PartialEq dedup in `daemon:status_changed` would then fire spuriously on every bus event.
Impact:   First call to `snapshot_to_dto` captures `now() - uptime` at that instant; subsequent calls return the cached value. Stable `started_at` makes the debouncer's PartialEq actually suppress duplicates.

## 2026-04-29 — Sesión 5
Decision: Use `notify-debouncer-mini = "0.4"` (NOT `-full`) with a 200ms window and **no** explicit tick rate.
Reason:   The 0.4 API is `new_debouncer(timeout, handler)` — there is no third `tick_rate` argument (the prompt's draft code mentioned one; the public crate doesn't expose it). YEAR1 work measured `mini` having lower lock contention than `-full` on monorepo workloads where tens of thousands of paths churn per second; `-full`'s per-path event buffering also surfaces rename pairs we don't need in v0.1. The 200ms window collapses VS Code / JetBrains save bursts (which fire create / modify / temp-file dance in <50ms) into a single delivery without delaying interactive feedback.
Impact:   `super::debouncer::DEBOUNCE_WINDOW = Duration::from_millis(200)` is the canonical constant. The `DebounceEventResult` is `Result<Vec<DebouncedEvent>, notify::Error>` — single error, not Vec — handled accordingly. Upgrading to debouncer-full later would require adapting the error path (it returns `Vec<notify::Error>`) and considering whether to surface rename pairs.

## 2026-04-29 — Sesión 5
Decision: `FsChangeKind` lives in `crate::daemon` (re-exported from `sensors::fs::kind`); the FS sensor depends on daemon, not the reverse.
Reason:   The IPC bridge (`ipc::events`) and future indexer (Session 6) need to pattern-match on `FsChangeKind` without crossing into sensor internals. Putting the canonical home at the daemon layer keeps the cross-sensor dependency direction one-way (sensors → daemon, never the reverse). `sensors/fs/kind.rs` is a thin re-export so callers reading the sensor module structure can still find the type locally.
Impact:   `crate::daemon::DaemonEvent::FsChange { kind: FsChangeKind }` and `crate::sensors::fs::kind::FsChangeKind` resolve to the same type. Sessions 6 (indexer) and 12 (procedural memory) consume from `daemon::FsChangeKind`. Variants: `Created` / `Modified` / `Deleted` / `Renamed { from: PathBuf }`. Today the watcher only emits `Modified` / `Deleted` (debouncer-mini's coarse `Any` events get classified by stat-checking the path post-debounce — `Created` is indistinguishable from `Modified` without tracking the previous file set, which is the indexer's job in Session 6); `Renamed` is reserved for a debouncer-full upgrade or platform-specific event paths.

## 2026-04-29 — Sesión 5
Decision: `DaemonEvent::FsChange { kind: FsChangeKind }` is serialized with `#[serde(rename = "change")]` on the `kind` field — the JSON wire field is `"change"`, not `"kind"`.
Reason:   `DaemonEvent` is internally tagged on `"kind"` (`#[serde(tag = "kind")]`). serde rejects a variant field of the same name as the discriminator. The Session 5 prompt explicitly requires the Rust field name `kind` (matching `FsChangeKind`'s natural name), so we keep the Rust API and rename only the wire field. No frontend code consumes `DaemonEvent::FsChange` yet (Session 14 builds the React shell), so the JSON shape is internal-only at this point.
Impact:   On the wire: `{"kind": "fs_change", "repo_id": "...", "path": "...", "change": {"kind": "modified"}}`. In Rust: `DaemonEvent::FsChange { repo_id, path, kind }` matches normally. The `daemon:event` Tauri channel delivers this shape to the webview; Session 14's frontend wrapper will pattern-match on `kind == "fs_change"` then read the inner `change` object.

## 2026-04-29 — Sesión 5
Decision: FS sensor actor runs on a dedicated `std::thread`, not under `tauri::async_runtime`. Cooperative shutdown via `cmd_rx.recv_timeout(150ms)` + bus-drain check for `DaemonEvent::Shutdown`.
Reason:   The actor's job is tiny (Attach / Detach / Shutdown). An async runtime would add an external dependency (tokio coloring) for no payoff: notify-debouncer-mini already runs its own thread internally for kernel event delivery. A 150ms tick gives shutdown latency well inside the daemon's 5s grace window with negligible CPU. Sync also makes the actor trivially testable — integration tests instantiate `EventBus` + `SharedDaemonState` directly and drive the handle without any runtime lifecycle.
Impact:   `FsSensorHandle` is `Clone` and lives in `tauri::State`; `attach`/`detach` calls from Tauri commands send through a `flume::Sender`. Dropping every clone closes the channel → actor sees `Disconnected` → exits. Production also exits on `DaemonEvent::Shutdown` from the bus. Both paths decrement `sensor_count` once.

## 2026-04-29 — Sesión 5
Decision: Initial walk runs on a `rayon::spawn` worker, not the actor thread. `MAX_FILES_HARD_CAP = 50_000` truncates pathological walks.
Reason:   The actor must stay responsive to Attach/Detach commands; a 5_000-file repo's walk is fast (~150ms) but nothing prevents a user from pointing the sensor at `~/` (tens of millions of files). Capping at 50_000 is generous for any realistic repo and keeps the perf budget (<120MB RAM idle) safe even when the indexer (Session 6) holds an embedding for every walked file. Truncation surfaces as a `SensorWarning` so the dock can prompt for a `.gitignore` rule.

## 2026-04-29 — Sesión 6

## 2026-04-30 — Sesión 9 (server-issued session_id, never trust the client)
Decision: `DaemonEvent::ShellEvent::session_id` is a server-assigned UUID v4, generated when the daemon accepts a connection on the local socket. The hook script does not send a session_id — even if it did, the daemon ignores it.
Reason:   The hook script runs in the user's shell and could be modified by anything in their `$PATH` ahead of `python3` (the canonical sender). Trusting the client to label its own session opens trivial spoofing — one shell could impersonate another's session by reusing its id. Server-assigned UUIDs scope every connection to its own listener-issued group, with no extra wire field to validate. Same security posture as `auth.json` for MCP and `git_hook_token` for Sesión 8 — the daemon is the source of trusted identity.
Impact:   Downstream consumers (memory layer, dock UI, analytics) group events by `session_id` knowing it strictly maps to one daemon-accepted connection. Reconnecting a shell (e.g. after `exec zsh`) yields a fresh `session_id` — the hook's perspective is "one connection per command burst", which the rate limiter (per-connection sliding window) already assumes.

## 2026-04-30 — Sesión 9 (privacy scrubbing in script, Rust port for tests)
Decision: Privacy-scrubbing of env-var-shaped secrets happens in the **shell hook script** before any data leaves the user's shell. The Rust function `installer::scrub_secrets` is the canonical regex specification and the test target; the shipped templates each implement an equivalent sed pipeline.
Reason:   The hook script is what the user can audit directly (`cat ~/.inari/shell/inari.zsh`). Putting the scrubber in the daemon would mean the daemon momentarily holds raw secret text, defeating the purpose: a crash dump or a `tracing::debug!` slip-up could leak. Scrubbing in the script keeps the daemon's input domain narrow (already-redacted text). Tests still need an executable specification; pure-bash sed regexes are clumsy to assert on, so the Rust port + 5-sub-test suite (`shell_secret_scrubbing.rs`) is the contract — any change to the regex changes both the Rust port and the script templates in lockstep.
Impact:   Future regex updates (e.g. handling lower-case env names or quoted multi-word values) edit `installer.rs::SECRET_RE` AND `resources/shell/inari.{zsh,bash,fish}` AND `resources/shell/README.md` in one commit. The README is the audit list users read — so changing it is part of the contract.

## 2026-04-30 — Sesión 9 (rate limit per-connection, never block the user's shell)
Decision: The 10-events/sec rate limit is enforced **per accepted connection** (a sliding-window `Vec<Instant>`). When the limit is exceeded, the offending event is dropped with a `tracing::warn!` line and the connection stays open. We never disconnect a chatty shell.
Reason:   Disconnecting on overflow would force the script to reconnect, which costs the user real prompt latency (the python3 client takes ~50-150ms cold). Worse, it would silently drop later legitimate events between the disconnect and the next reconnect. Drop-but-keep-alive trades a bounded amount of telemetry loss for guaranteed shell responsiveness — same trade-off the bus broadcaster makes (drop-oldest under back pressure, never block the producer).
Impact:   A `for i in {1..1000}; do echo $i; done` loop produces ≤ 10 events/sec on the bus; the other 990 are logged and discarded. The rate-limiter test (`socket::tests::rate_limiter_allows_burst_then_blocks`) pins the burst capacity + window. If a future session needs higher throughput (e.g., for power users running heavy benchmark scripts), it raises `RATE_LIMIT_BURST` / `RATE_LIMIT_WINDOW_MS` constants — same SSOT.

## 2026-04-30 — Sesión 9 (events table persistence vs bus SSOT)
Decision: Each accepted shell event is published on the bus AND inserted into the `events` table (`kind = "shell_event"`, `repo_id = NULL`, JSON payload). The bus publish is the single source of truth; the SQL row is a non-fatal best-effort.
Reason:   The bus is in-memory and ephemeral — once consumed by a subscriber, the event is gone. The `events` table gives the analytics + memory layers a queryable history that survives daemon restart. Persisting both keeps the runtime semantics identical to today (live consumers see live events on the bus) while building the audit/replay surface future sessions need. Inserting *only* into SQL would add latency to consumers that don't care about history (the dock); inserting *only* into the bus would lose every event the second the daemon restarts.
Impact:   The `events` table is the canonical store for shell history. The TTL retention sweep (30 days per spec recap) is NOT shipped this session — see HANDOFF "Blockers / deferred". The first session that adds a generic `events` retention cron sweeps `kind = 'shell_event'` rows older than 30 days. Persistence failure is logged at `warn` and never closes the connection — bus consumers stay live even if SQLite is full or read-only.

## 2026-04-30 — Sesión 9 (cross-platform via `interprocess`, single SocketName enum)
Decision: Cross-platform local sockets (Unix domain socket / Windows named pipe) via the `interprocess` crate's `LocalSocket*` API. The platform leak is contained in `SocketName::SocketNameKind { FsPath, Namespaced }`; `spawn`, `spawn_at_name`, and `handle_connection` are platform-agnostic.
Reason:   `interprocess` is the same crate Datadog/Cilium/Cloudflare use for their local-socket IPC. It dispatches automatically on platform: `GenericFilePath` → AF_UNIX on Linux/macOS, `GenericNamespaced` → `\\.\pipe\<name>` on Windows. Hand-rolling per-platform `cfg` branches at every call site (open, accept, connect) would be ~150 LoC of duplication and a platform-conditional bug surface. The dep is small (no transitive monsters) and stable (2.x has been out since 2024-10).
Impact:   Tests use the same `SocketName::connect()` helper on both platforms, with the only `cfg` branch being the `make_test_socket` helper in test files (Unix uses a tempdir path, Windows uses a UUID-suffixed namespaced name). Future shell-related sensors (e.g. an HTTP-proxy sensor wanting a similar local-socket transport) can reuse `SocketName` verbatim.

## 2026-05-01 — Sesión 10 (backend selection: local-binary-first, remote fallback, inert third)
Decision: `sensors::substrate::replay_client::auto_backend()` resolves the replay backend in this order: (1) `LocalReplayBackend` if `substrate-v2-replay` is on PATH (or `INARI_REPLAY_BINARY` points at a real file), (2) `RemoteReplayBackend` if BOTH `INARI_STAGING_URL` and `INARI_STAGING_TOKEN` are set, (3) no backend → the actor still spawns and counts as a sensor but never publishes a `ReplayResult`.
Reason:   Local exec is fastest (~100ms cold, no network) and works fully offline once the binary is installed. The "inert third" path is the safety valve: a clean install with neither configured should NOT noisily fail or block startup — the dock's "Replay-as-you-code" toggle is opt-in (per-repo `replay_enabled` flag, default false post-migration-0004), so a user who hasn't opted in pays nothing for the sensor's existence.
Impact:   The actor is backend-aware via a single `Box<dyn ReplayBackend>` field. Production swaps backend via env vars without a code change; tests inject a mock `ReplayBackend` (closure-driven) via `spawn_with_backend`. ## 2026-05-01 — Sesión 10 (DivergenceSummary on the bus, full payload on disk)
Decision: `DaemonEvent::ReplayResult` carries only metadata (`{kind, affected_module, severity}` plus the bare recording id). The full divergence payload — including any recorded body data, source snippets, and raw timings — lives in `<repo>/.inari/replays/<recording_id>.json` for the dock UI (Sesión 17) to load on demand. `affected_module` is a Node-style module name (`express/router`, `next/api`), NEVER a file path — keeps absolute paths off the bus.

## 2026-05-01 — Sesión 10 (retention as a sibling task, not a cron job)
Decision: Hourly recording-retention runs as a tokio task spawned from `sensors::substrate::spawn_with_backend`, not as a cron job in the Go scheduler or a `setInterval`-style timer in the daemon lifecycle. The task subscribes to the bus to (a) discover repo roots via `FsChange::path → repo_root_of_path`, and (b) honour `DaemonEvent::Shutdown`. Recordings older than 7 days are deleted from `.inari/recordings/`; failures are logged at `warn` and skipped (next sweep retries).
Reason:   Cron-on-host couples retention to the daemon's deployment; an offline laptop closed for 8 days would never run the sweep, leaving recordings to accumulate. An in-process tokio task runs whenever the daemon is alive, which is the only time recordings can be CREATED in the first place — symmetry of producer + consumer. The bus-driven repo discovery means we sweep only repos the user has actually opened/touched recently; we never sniff the disk looking for `.inari/` directories outside that signal. This keeps the retention task scoped to data the user is currently working with, not historical projects on the same machine.
Impact:   The retention task is `JoinHandle<()>` owned by the actor's outer task; on `Shutdown` the actor `abort()`s it. First sweep fires after one full hour (the `tick.tick().await` skipped first-fire pattern) so quick test runs don't trip on a prune side-effect. The 7-day window is hard-coded (`RECORDING_RETENTION` const); making it user-configurable lands in Sesión 17 alongside the per-repo toggle. Recordings deleted are logged with `tracing::info!` for audit but NOT persisted as `events` rows — a deletion is a maintenance action, not user-visible state.

## 2026-05-01 — Sesión 15 (segmenting messages by hand instead of `react-markdown`)
Decision: `ChatMessage.tsx` segments the assistant's content into `text` and `code` blocks via a hand-rolled regex (`/```([a-z0-9_-]*)\n([\s\S]*?)```/g`). The fenced-code block is rendered with Shiki + a copy button; everything else is rendered as a `<p>` with `whitespace-pre-wrap`. `react-markdown` and `remark-gfm` are in `package.json` from Sesión 14 but not imported by Sesión 15.
Reason:   The dock's chat surface is constrained — fenced code is the only structured element it renders today (the Anthropic / Devin / Linear chat surfaces all start here, then expand). Two factors pushed against `react-markdown` for this milestone:
  * **Streaming reflow.** `react-markdown` reparses the entire string on every token, which means each appended token redraws the full message tree. The hand-rolled segmenter only re-walks the regex; partial fences in mid-stream stay as plain text until the closing ``` lands, so the layout doesn't twitch as code blocks "appear" mid-paragraph.
  * **Bundle weight.** `react-markdown` + `remark-gfm` add ~50KB gzipped on the dock entry, the bundle Sesión 16 / 17 will keep adding to. Deferring the import until structured prose features (headings, lists, links) actually need rendering keeps the dock chunk small.
Impact:   When Sesión 16 / 17 add a feature that needs lists or headings (Postmortem viewer, Memory.md preview), they import `react-markdown` lazily for those screens — NOT into `ChatMessage`. If they need it for the chat surface specifically, the swap is local: replace the `text`-block branch in `ChatMessage.tsx::segmentMessage` with a `<ReactMarkdown>` render. Code-block extraction continues to use the regex (Shiki integration via `react-markdown`'s `components.code` is more verbose than the current direct call). The current path keeps streaming throughput high; the upgrade path is one localized change.

That's a Sesión 19 responsibility (it owns "give the AI memory of past conversations"), not a Sesión 13 one.
Impact:   `events` table stays bounded by sensor rates (low Hz). When S19 wants the audit trail, the recipe is documented in `memory/episodic/mod.rs` head: publish `DaemonEvent::ChatSessionFinished { session_id, prompt, response, prompt_tokens, completion_tokens, cost_cents }` from `streaming.rs` on the closing chunk, and add the `chat_session` arm to `kind_tag` + `ttl_for(90 days)` in retention. The 90-day TTL was the spec target — preserving the design intent without paying the row-cost today.

## 2026-05-01 — Sesión 13 (retention runner: 1-hour cadence + 10 000-row VACUUM threshold; both hard-coded)
Decision: `TICK_INTERVAL = Duration::from_secs(3600)`. `VACUUM_ROW_THRESHOLD = 10_000`. Neither is settings-backed; changing them requires a code change.
Reason:   The events table grows at low Hz on a healthy dev box (FsChange + ShellEvent + GitEvent). Faster wakes (every minute) save kBs of disk for hours of background CPU; slower wakes (daily) let an `npm install` shell-event burst sit around for the better part of a day before pruning. One hour is the sweet spot. The VACUUM threshold is the same logic — VACUUM rewrites the file, which is fine sub-second on a small DB but worth amortising; under the threshold (typical retention tick = a few hundred rows) we let SQLite reuse free pages organically. Hard-coding both removes a runtime-tuning surface that has no real diagnostic value: telemetry never showed "users want to tune the retention cadence" because users do not interact with it.
Impact:   If the cadence ever proves wrong (e.g. a future high-rate sensor like keystroke logging lands), the change is a 1-line PR. The constants are exported `pub` so tests + future callers can reference them rather than hard-coding magic numbers themselves.

## 2026-05-01 — Sesión 13 (TTL table source — locked from HANDOFF spec, hard-coded as `match` arms)
Decision: `crate::memory::retention::ttl_for(kind: &str) -> EventTtl` is a closed `match` over the persisted-kind tag strings. Adding a new persisted kind requires editing both `kind_tag` (in episodic) and `ttl_for` (in retention).
Reason:   The TTL table in HANDOFF Sesión 13 spec is a product decision (privacy / compliance / debug-window) not an implementation detail. ## 2026-05-01 — Sesión 13 architect follow-up (test fixture normalised to match production embedding contract)
Decision: `tests/semantic_search_top_k.rs::make_embedding(score)` now L2-normalises the synthetic vector before returning. The `code_embeddings` virtual table in `0002_embeddings.sql` does NOT specify a `distance_metric=` — sqlite-vec defaults to **L2**, not cosine (despite the prose comment in `queries.rs:459`). Production is correct because fastembed always returns unit-norm vectors, and for unit-norm vectors L2 ranking ≡ cosine ranking. The original test used un-normalised `[score, 1, 0, …]` vectors, so the L2-nearest result was the lowest-magnitude vector (PRIMARY at score=1.0, L2≈1.0) instead of the highest-cosine vector (OTHER at score=2.0, L2≈1.414).
Reason:   Two clean ways to fix this: (a) normalise the test fixture to mirror fastembed's contract, or (b) add `distance_metric=cosine` to the vec0 table via a new migration + a full reindex. (a) is a one-function change with zero production impact; (b) would touch every embedding ever stored, requires a migration that downstream consumers have to opt into, and there is no functional change for unit-norm inputs anyway. (a) wins on cost. The cosmetic comment in `queries.rs:459` should be corrected in a future cleanup pass — flagged in HANDOFF Sesión 13 *Test fix* block.
Impact:   `make_embedding` is now `[score / √(score²+1), 1 / √(score²+1), 0, …]`. The 5 S13 tests pass end-to-end (semantic 2 + episodic 1 + retention 2). Perf observed on the semantic test: 0.76 ms cold, 4.03 ms warm-cache — both ≪ the 100 ms target on the 50-primary + 10-noise fixture, well within budget for S19's remediation context-gather flows.

## 2026-05-01 — Sesión 19 (apply path: `git apply --check` first, no `--no-verify`)
Decision: `orchestrator::apply_diff` runs `git apply --check <patch>` before the real `git apply`, then `git add <files>` (only the files the diff touched, never `-A`), then `git commit -m <msg>` WITHOUT `--no-verify`. NO `git push`.
Reason:   `--check` is the deterministic gate — if the diff is malformed, applies to a different file revision than the AI thought, or hits a binary file mid-hunk, we want to fail BEFORE writing to the working tree. Failing during `git apply` (no check) leaves the user's tree partially patched, which is the worst possible state to be in (the dock shows "applied" but the disk says half-applied). The two-step pattern is the same one `git rebase --interactive` uses internally. `git add <files>` instead of `-A` is a path-traversal defence in depth: if a hostile model managed to slip an extra file path past `parse_diff_files`, `-A` would stage it; `add <files>` only stages what the parser saw. `--no-verify` is intentionally omitted — user pre-commit hooks should still run on Inari-generated commits, both because the user trusts those hooks and because a broken pre-commit hook (lint failure on the AI's output) is a signal worth surfacing to the user, not silencing. NO push: pushing is a Sesión 20 (gate-runner) concern, not Sesión 19's. The user manually runs `git push` after the dock shows the success toast, which gives them a chance to review the commit and bail if needed.
Impact:   `desktop/src-tauri/src/ai/remediate/orchestrator.rs::apply_diff`. Test `tests/apply_diff_to_disk.rs` validates the happy path; `tests/apply_diff_rejects_path_traversal.rs` validates the security gate fires before any disk write.

## 2026-05-01 — Sesión 12 (in-memory cache + write-through, NOT shared with matcher)
Decision: The learner keeps an `Arc<RwLock<HashMap<RepoId, PatternsFile>>>` write-through cache. The matcher does NOT read from this cache — it loads patterns from disk on every call.
Reason:   Cache reduces disk I/O during burst writes (e.g., a CI pipeline that surfaces 10 errors → 10 fix attempts → 10 `RemediationCompleted` events). The matcher is on the read side and is called by Sesión 19's context-gather step at most once per remediation; a single file load (≤ 500 patterns × ~200 bytes ≈ 100 KB) is well under 1 ms. Sharing the cache across modules would couple them and require either a global `OnceLock` or threading the cache reference through every matcher caller. Decoupled v0.1 is simpler; if a benchmark ever shows the read path needs the cache, lifting it is a localised change.
Impact:   `memory/procedural/learner.rs::with_repo` owns the cache; `memory/procedural/matcher.rs::match_patterns` reloads from disk via `learner::load_patterns`. The two modules share `load_patterns` / `save_patterns` / `patterns_path` as the only seam.

## 2026-05-01 — Sesión 12 (floats banned from on-disk patterns.json; ranking uses f64 in memory only)
Decision: All numeric fields in `Pattern` + `PatternsFile` are integer (`u32`/`i64`). The matcher's `score` and `recency_weight` are computed at call time as `f64` and never written to disk.
Reason:   The HANDOFF spec required "no float precision drift" on roundtrip (load → save). The cleanest way to guarantee that by construction is to forbid floats in the on-disk shape entirely — there's no quantisation rounding to argue about. Ranking still benefits from continuous `f64` math (recency half-life, success-rate proportion) so we use it in memory; the score is a derived value, not state.
Impact:   `Pattern { success_count: u32, failure_count: u32, last_seen_ms: i64, created_at_ms: i64 }`. The roundtrip integration test (`save_load_save_is_byte_identical`) enforces the no-drift invariant on every CI run.

## 2026-05-01 — Sesión 12 (anti-pattern rows are exempt from pruning)

Reason:   An anti-pattern is a "do NOT try this fix" lesson. Forgetting one would let a known-bad fix re-surface — strictly worse than the few extra KB of disk it costs to keep the row indefinitely. ## 2026-05-01 — Sesión 12 (recency half-life = 30 days; Wilson lower bound deferred)
Decision: Matcher ranking uses `score = success_rate * exp(-age_days / 30)`. Simple proportion `success / (success + failure)` for the rate; no Wilson lower bound or other small-sample correction.
Reason:   30-day half-life balances "recent is better" with "code change cadence is real" — a 30-day-old pattern still scores 0.5 of a fresh one (still relevant), while a 90-day-old one scores 0.125 (significantly downweighted). Wilson lower bound is the correct estimator when sample sizes are tiny (n<10) and you want to be conservative about high success rates with low evidence; for v0.1, dataset sizes are too small to make the calibration worth the complexity. Reopen when (a) the dataset exceeds 1000 patterns AND (b) we observe a real case where simple-proportion ranking surfaces a bad recommendation.
Impact:   `memory/procedural/matcher.rs::rank_patterns` + `RECENCY_HALFLIFE_DAYS = 30.0`. The unit test `fresh_high_rate_outranks_stale_perfect` locks the formula by asserting fresh 0.9 (raw) ≡ 0.9 (weighted) > stale 1.0 (raw) ≡ 0.25 (weighted at 60 days).

## 2026-05-01 — Sesión 22 (LSP TCP listener is the canonical transport; stdio is a passthrough sidecar)
Decision: The LSP server binds TCP on `127.0.0.1:9877` from inside the Tauri daemon process. Editors that drive LSP over stdio (VS Code, Cursor, Zed, Neovim's lspconfig defaults, JetBrains, Helix) launch the `inari-lsp-stdio` sidecar binary, which is a dumb byte-pump between stdin/stdout and the TCP socket. The sidecar does NOT parse frames.
Reason:   The Inari Live daemon must serve multiple editor windows + the dock UI simultaneously without spawning a fresh server per editor session. A single shared TCP listener fans out trivially via `tokio::spawn` per accepted connection. Stdio LSP, in contrast, is single-tenant: one process per editor session. Forcing the daemon to spawn a fresh in-process LSP for every editor would (a) duplicate the indexer/memory/AI state per stdio session, (b) require the daemon to track a stdio-server pool, and (c) break shared cancel/document-cache state between the dock and editor. The byte-pump sidecar (~80 LoC, no LSP awareness) lets stdio editors connect to the shared in-process server and means the sidecar never has to be re-released when the wire format evolves — only the daemon does.
Impact:   `desktop/src-tauri/src/bin/inari_lsp_stdio.rs` is the sidecar. `INARI_LSP_HOST` + `INARI_LSP_PORT` env vars override the defaults (127.0.0.1:9877). The daemon binds in `lib.rs::start_lsp_listener` and is fail-OPEN — bind failure (e.g. another instance already running) logs but does NOT abort the daemon. Tests use `lsp::start_lsp_server_for_test()` which binds on port 0 and returns the bound `SocketAddr` + a state handle.

## 2026-05-01 — Sesión 22 (cancellation = `oneshot::Sender<()>` per pending request, NOT `tokio_util::CancellationToken`)
Decision: The LSP cancel mechanic is a per-request `oneshot::channel::<()>` registered in `LspState::pending: Mutex<HashMap<RequestId, oneshot::Sender<()>>>`. Handlers run inside `tokio::select! { work => ..., cancel_rx => RequestCancelled }`. `$/cancelRequest` removes the entry and fires the sender.
Reason:   A `oneshot` is a single-shot signal — exactly the cancel semantic we need (one cancel per request id). `tokio_util::CancellationToken` is multi-shot (clone + drop tracking) and pulls the entire `tokio-util` crate into the dep graph for a feature we use exactly once per request. The `oneshot` is in tokio core (already a dep). The single-shot semantic also makes it impossible to accidentally cancel a request twice, which is a real bug class with multi-shot tokens.
Impact:   `LspState::register_pending(id) -> oneshot::Receiver<()>` + `complete_pending(id)` + `cancel(id)`. Duplicate-id registration drops the older sender (broken-client tolerance). `complete_pending` is called by every request path (success or error) so the map does not leak. The pattern is identical to the one S23+ will use to wrap `LocalAI::generate` calls in cancel-awareness.

## 2026-05-01 — Sesión 22 (test-only `completion_delay_ms` knob lives on `LspState`, not behind a cargo feature)
Decision: `LspState::set_completion_delay_ms(u64)` + `completion_delay_ms()` are public methods on the production type. The completion handler reads the knob; production code never writes it.
Reason:   The cancel test needs the completion request to be observably pending so the cancel-then-wait race is real (otherwise the stub returns instantly and the cancel is a noop on the wire — passing for the wrong reason). Options were (a) gate the field behind `#[cfg(any(test, feature = "test-helpers"))]` + `cargo test --features test-helpers`, (b) inject a test hook via a function pointer, (c) just expose the knob and not write it in production. Option (a) breaks integration-test compilation because integration tests don't have `cfg(test)` set on the linked lib crate AND can't depend on themselves with a feature flag. Option (b) adds indirection (boxed closure stored on state) for a feature only ever exercised by one test. Option (c) is one `AtomicU64` on the state struct (~8 bytes, branch-predicted-zero load on every completion) — by far the simplest. The same pattern lands on every test-only knob the LSP server may grow.
Impact:   `lsp::LspState::completion_delay_ms: AtomicU64` (default 0). The completion handler does `if delay > 0 { sleep }` which is a no-op in production. If the knob ever leaks to a UI, that's a data-loss-class bug, but it's behind 5 letters of method name (`set_completion_delay_ms`) — easy to grep before release.

## 2026-05-01 — Sesión 22 (per-connection writer is mpsc-serialised so handlers can complete out of order)
Decision: Each TCP connection in `lsp::handle_connection` splits into `(read_half, write_half)`. The write half is owned by a single `tokio::spawn`-ed task that drains an `mpsc::UnboundedSender<Vec<u8>>`. Every request handler completes via that channel. Notifications go through the same channel.
Reason:   LSP requests can complete out of order (request id 5 may finish before request id 4 if the model call for #4 takes longer). Writing to the same TCP socket from multiple handlers concurrently would interleave bytes mid-frame and corrupt the wire. The mpsc serialises writes without forcing handlers to complete in registration order. Using `tokio::sync::Mutex<WriteHalf>` would also work but turns every write into a contended lock acquisition; the unbounded mpsc is lock-free on the producer side and lets the writer task batch flushes if needed in a future iteration.
Impact:   `lsp::handle_connection::out_tx` is the canonical out-of-band emit point. S23+'s `$/progress` token-stream notifications use the same channel. If a future bug ever shows interleaved frames, the cause is NOT this design — check whether someone bypassed the channel and wrote directly to the half.

## 2026-05-01 — Sesión 22 (LSP positionEncoding = utf-16; document store stores UTF-8 strings + converts at the boundary)
Decision: The `initialize` capability advertises `positionEncoding: "utf-16"` (LSP 3.17 default). Documents are stored internally as UTF-8 `String`. Every `Range`-based edit goes through `lsp::document_sync::utf16_pos_to_byte` which walks UTF-16 code units inside the target line.
Reason:   utf-16 is the default offset encoding LSP clients send when no negotiation happens — every editor on the planet supports it. Negotiating utf-8 (the better encoding for our internal storage) would require client cooperation and would not work for editors that don't implement the `positionEncoding` client capability. Storing documents in UTF-8 keeps the bytes ergonomic for downstream Rust string processing (FIM prompt construction in S23, the indexer's tree-sitter parser, etc.) — converting once at the edit boundary is a known, fast operation. The conversion handles BMP (e.g. `é` = 1 UTF-16 code unit, 2 UTF-8 bytes) and astral characters (e.g. `🦊` = surrogate pair, 4 UTF-8 bytes); both cases are unit-tested in `document_sync::tests`.
Impact:   `lsp/document_sync.rs::utf16_pos_to_byte`. If a client ever negotiates utf-8 (Sesión 24+'s context-selection optimisation might want it), add a `position_encoding: PositionEncoding` field to `LspState` and branch in the converter — but for S22 no negotiation, no branch.

## 2026-05-01 — Sesión 23 (`extract_context` uses line-indexed math, not newline-counting walk-back)
Decision: `lsp::fim::extract_context(text, byte_offset, lines_each_side)` builds a `Vec<usize>` of line-start byte offsets in one pass, binary-searches the cursor's line, then slices `start_line = cursor_line - N` through `end_line = cursor_line + N` (clamped to doc edges). The cursor's own line is included in BOTH halves of the slice — prefix gets `start_line..cursor`, suffix gets `cursor..end_of(end_line)`.
Reason:   The naive "walk back N newlines from cursor" implementation has a load-bearing edge case: cursor at column 0 of line K and N=2 should land at start-of-line(K-2), but stepping back over 2 newlines lands at start-of-line(K-1) (one newline-cross is the cursor's own line boundary). Line-indexed math sidesteps the off-by-one entirely AND makes the test expectations obvious: "lines K-N through K+N around cursor". The single-pass O(text.len()) precompute is cheap (a 4 MB document — VS Code's open-file cap — has ~150k lines, negligible alloc) and runs once per completion.
Impact:   `lsp/fim.rs::extract_context`. Eight unit tests pin behaviour at the edges (empty text, out-of-range cursor, doc start/end, mid-line cursor, zero-N degenerate). S24 swaps the slice for indexer-aware top-3-symbols context — the contract `(prefix, suffix) -> String` of `build_fim_prompt` survives unchanged so the swap is local.

(2) Server-side decoding of the segment via `params` — rejected; the segment encodes the receipt JSON, and pushing it through the SSR pipeline would log it to server access logs (privacy footgun). (3) Hash-routing (`#r=<base64>`) — rejected; not URL-safe to share, and Twitter's link previewer strips the fragment. ## 2026-05-01 — Sesión 29 (`POST /api/verify` accepts JSON body, multipart `file`, multipart `receipt`, x-www-form-urlencoded; GET takes `?json=…`)
Decision: The server-side endpoint has FOUR input shapes. The route uses `new URL(req.url).searchParams` (not `req.nextUrl.searchParams`) so `Request`-backed test doubles work without polyfilling Next-specific properties. CORS is open (`*`) — the response is a verdict on a public receipt, not a privileged action.
Reason:   The spec asked for "JSON body OR multipart file." Adding the `receipt` form-field path lets a curl one-liner work without juggling boundary delimiters (`curl -d "receipt=$(cat r.eap.json)"`). The GET path makes the endpoint diagnosable by hand without crafting a body — useful when an auditor is verifying via shell history or wants to share a curl-able link. Disclosure footer ships in both the success and the 4xx-error JSON bodies, so even on a 400 (`empty body`) the policy field is present. ## 2026-05-01 — Sesión 24 (context selection uses parser-only, NOT semantic embeddings)
Decision: S24's indexer-aware context (`fim::build_context_for_completion`) calls `crate::indexer::parser::parse_file(lang, source)` on the OPEN DOCUMENT'S text in-memory — no Store handle, no `embed_one`, no pgvector / KNN search. The "top-3 relevant symbols" come from the symbol table extracted from the same buffer the user is editing, ranked by per-language priority + name-mentioned-in-prefix + proximity-to-cursor.
Reason:   The HANDOFF S24 spec said "use the indexer (S6) to retrieve top-3 relevant symbols". `indexer/` exposes two retrieval surfaces: (a) `parser::parse_file` — pure tree-sitter, no I/O, ~5 ms; (b) `semantic::search` — requires `&Store`, async-blocking on `embed_one` (3-8 ms), needs `repo_id` mapping from the LSP URI. Wiring (b) into the LSP completion pipeline would require: (1) plumbing `Arc<Store>` through `LspState` (constructor change), (2) URI → repo_id resolution every keystroke (DB query), (3) `tokio::task::spawn_blocking` for the embedder, (4) handling the case where the repo isn't indexed yet (graceful fallback). All four cost session time AND latency in the 250 ms hot path. Option (a) is the right cardinality for S24: same indexer module, the model still sees structural context (interface defs, helpers, imports), latency stays sub-10 ms, no cross-cutting wiring. Cross-file semantic retrieval is a v0.3 follow-up if quality demands it.
Impact:   `desktop/src-tauri/src/lsp/fim.rs` adds `build_context_for_completion(text, byte_offset, lines_each_side, Option<Lang>) -> (String, String)` that returns the same `(prefix, suffix)` pair as `extract_context` but with a header (top-3 symbols + import block, comment-prefixed) prepended to `prefix`. Per-language tuning lives in the `SymbolFilter` priority table. `LspState` does NOT grow a Store field. Falls back to the S23 ±200-line slice when language is unknown OR the parser yields no relevant symbols.

## 2026-05-01 — Sesión 24 (smart triggers — tree-sitter ancestor walk, NOT regex / character class probes)
Decision: `lsp::triggers::should_trigger` decides suppression in two stages: (1) byte-level mid-word check (cheap, language-agnostic ASCII identifier rule), (2) tree-sitter parse + `descendant_for_byte_range(off, off)` + walk the ancestor chain matching against per-language node-kind sets (`string`, `comment`, `import_statement`, etc.). NO regex-based `"in a string"` heuristics, NO `// looks like comment` line-prefix probes.
Reason:   Regex / line-prefix heuristics get the easy cases right but break on real code: backslash-escaped quotes inside strings, `//` URLs inside string content, JSX text that LOOKS like a comment, Python f-strings with embedded expressions. Tree-sitter's grammar already captures the precise scope semantics each language defines and the indexer (S6) ships the 5 grammars we need — reusing them avoids duplicating language knowledge. The cost is ~1-3 ms per parse on a 4 MB document (well under the 250 ms budget). The mid-word check stays as a pre-filter because tree-sitter's `identifier` node alone doesn't tell us "the cursor is BETWEEN characters of a word vs at the boundary"; that's a position-relative-to-bytes question, not an AST question.
Impact:   `desktop/src-tauri/src/lsp/triggers.rs` (NEW) — `should_trigger(language_id, text, byte_offset) -> bool` + per-language suppression sets. Files in unrecognised languages skip the AST stage and only block mid-word. The 6 integration tests cover all 4 suppression contexts (string, line/block comment, mid-word, import block) across TS / Rust / Python / Go.

## 2026-05-01 — Sesión 24 (ranking is single-score additive, NOT a multi-criteria sort)
Decision: `candidate_score(completion, prefix, suffix, lang) -> i64` returns a single integer; the ranker picks `argmax`. Components: `+10` if completion ends on a non-identifier boundary, `+10` if `tree-sitter parse(prefix + completion + suffix)` reports no errors, `-5` per overlap-with-prefix 20-char window (capped at 3), `+1` per novel identifier in the completion (capped at 3), `-3` for empty/whitespace-only.
Reason:   A multi-stage tuple sort (kind first, then validity, then overlap, then novelty) is more expressive but harder to tune — a single tweak in any layer reorders everything underneath. A summed score lets each criterion contribute independently and makes the relative weights visible at the call site. `+10`s dominate the dial (token-boundary + syntactic validity together can swing a candidate past anything else), `-5` overlap is enough to beat one boundary win, novelty is a tiebreaker for otherwise-equivalent candidates. When acceptance ratio data lands post-S31 we can re-tune by editing constants — the algorithm doesn't change.
Impact:   `lsp/handlers/completion.rs::candidate_score` + 2 unit tests pinning expected ordering. Empty / whitespace-only candidates are explicitly down-weighted so a stuck mock or a model that "thinks for too long and outputs nothing" can't accidentally win the ranking.

## 2026-05-01 — Sesión 24 (n=3 sampling via `tokio::spawn`, not via llama-server's `n` parameter)
Decision: The pipeline calls `LocalAI::generate` THREE times in parallel with `temperature: Some(0.7)`, each call wrapped in its own `tokio::spawn`. We do NOT request `n: 3` server-side via llama-server's parameter — we issue three independent HTTP requests.
Reason:   llama-server's `/completion` endpoint does support a `n` parameter (returns `n` candidates in one response) but it (a) serialises the generation server-side (no parallelism on the GPU; one prompt, three sequential decodes), and (b) returns them in a single non-streaming JSON blob, breaking the SSE contract `LocalAI::generate` already speaks. Issuing three parallel HTTP requests gets actual GPU parallelism on the CUDA path (the runtime can batch the three prompts), works on llama-server versions that don't ship the `n` knob, and reuses the existing SSE stream parser without a new code path. The cost is 3× connection overhead — measured ~8 ms total on a localhost socket; well under the 250 ms budget. If a future session sees connection-pool exhaustion under heavy use, switching to `n: 3` is a one-line change in `local_ai/mod.rs`; the ranker doesn't care where the candidates came from.
Impact:   `lsp/handlers/completion.rs::sample_n_candidates` + `GenerateOptions::temperature: Option<f32>`. The 3 callers of `GenerateOptions` (S23 completion handler, S25 future Apply, the `local_ai_streams_completion.rs` test) gain a new field. Existing call sites set `temperature: None` (lets llama-server use its default). The S24 sampling site is the only `Some(0.7)`.

## 2026-05-01 — Sesión 24 (cache lookup BEFORE the cancel-aware select, NOT inside it)
Decision: `compute_completion` consults the LRU cache (`state.completion_cache().get(&key)`) BEFORE entering `tokio::select!` against `cancel_rx`. A cache hit returns synchronously without registering the cancel race; a miss falls through to the n=3 + ranking pipeline that IS inside the select.
Reason:   A cache hit is sub-millisecond. Wiring it inside `select!` would mean: (a) the editor sends `$/cancelRequest` in the same network round-trip as the next keystroke, (b) the cancel arrives before our success arm wakes, (c) we'd respond with `-32800 RequestCancelled` for a request whose result was ALREADY computable in zero time. From the editor's POV that's a regression: VS Code briefly clears its completion popup on cancel, then the next keystroke fires another request. Returning the cached value beats the cancel by orders of magnitude on the wire — the editor never sees the cancel because the response hits first. The cache being pre-cancel does NOT defeat S22's regression test: that test sets `completion_delay_ms` BEFORE the LocalAI call (and now BEFORE the cache lookup too), so cancel still wins against the artificially-slowed handler.
Impact:   `lsp/handlers/completion.rs::compute_completion` consults cache after the delay-knob sleep but before any further work. Cancel still owns the LocalAI call AND the ranking + dedup stage. The S22 cancel regression remains byte-identical in observable behaviour (the cache is empty on first call, so the second cancel-test request follows the slow path).

## 2026-05-01 — Sesión 24 (250 ms latency budget — silent timeout, NOT escalated as JSON-RPC error)
Decision: The whole post-cache, post-trigger pipeline is wrapped in `tokio::time::timeout(Duration::from_millis(250), run_pipeline(..))`. Timeout returns the empty CompletionList — same silent-degradation path as every other failure (no LocalAI, no document, parser fail, all candidates empty/duped).
Reason:   Cursor users have measured "Tab feels native at <150 ms TTFT, frustrating at >250 ms". A pipeline that takes 800 ms because the model's GPU is paged out is NOT a useful completion — it lands after the user has typed past it AND blocks the next request from registering. Empty list lets the editor fall back to its built-in suggestions; the user keeps moving. Surfacing the timeout as a JSON-RPC error would force editors to decide what to display (most show a banner — that's user-visible noise). The S23 decision "completion failures degrade silently" extends naturally here. The 250 ms ceiling sits ABOVE the S22 `completion_delay_ms` test knob (which is 500 ms in the regression) — the test bypasses the budget by virtue of running before the timeout starts.
Impact:   `lsp/handlers/completion.rs::compute_completion` wraps `run_pipeline` in `tokio::time::timeout`. The cancel `select!` is OUTSIDE the budget timeout (cancel can fire faster than 250 ms). Future tuning: if telemetry shows acceptance ratio is bottlenecked by timeouts on cold-start, raise the budget to 350 ms — the model doesn't need to be tuned, the timeout does.

## 2026-05-01 — Sesión 26 (RepairError taxonomy: Truncated + FullRewriteSuspicious are FATAL, PartialChatMLEmission + EmptyOutput are RECOVERABLE)
Decision: `diff_repair::RepairError` is a 4-variant enum split into two semantic classes. **Fatal** (no retry — bail straight to cloud): `Truncated { original_len, edited_len }` (when `edited.len() < 0.5 × original.len()` AND `original ≥ 200B / 5 lines`), `FullRewriteSuspicious` (when EVERY non-trivial line of original is missing from edited AND original ≥ 10 lines AND instruction has no `rewrite|redo|from scratch` keyword). **Recoverable** (retry with `build_kortix_repair_prompt`): `PartialChatMLEmission` (any `<|im_start|>` / `<|im_end|>` / `<|im_` marker in body slice excluding the trailing 16 bytes — S25's `strip_chatml_trailer` owns that region), `EmptyOutput`.
Reason:   The split mirrors WHY each failure happens. Truncation = the model's stream cut off mid-output (network drop, context-length exhaustion, tokeniser glitch); a second 180-second wait won't change the prompt distribution. Full rewrite = the model hallucinated the wrong scope (it rewrote the whole file when asked for a one-line fix); the same prompt would produce the same wrong scope on attempt 2 — the only fix is a cloud model with a longer context window and stronger instruction-following. PartialChatMLEmission = a transient tokeniser hiccup the model can correct when explicitly told "don't emit control tokens"; EmptyOutput = a transient sampling collapse the model recovers from when prompted "your previous output was empty". The retry-vs-bail distinction is the difference between "wasting one ~3-minute window" and "wasting two" — locking the taxonomy now prevents future sessions from re-classifying without measurement.
Impact:   `desktop/src-tauri/src/ai/diff_repair.rs::RepairError` is the SSOT. `single_shot::try_fast_apply_local` matches against the variants explicitly: `Err(RepairError::Truncated{..}) | Err(RepairError::FullRewriteSuspicious) => return None;` // straight to cloud. `Err(_)` → loop another attempt (subject to MAX_LOCAL_ATTEMPTS). The 20-case sweep test (`tests/apply_v2_apply_rate_sweep.rs`) locks 3 fatal-class scenarios (D1-D3) — adding a 5th RepairError variant must extend the sweep with a matching scenario.

## 2026-05-01 — Sesión 26 (normalisation pipeline = BOM strip → CRLF/LF unify → align to original; runs BEFORE all detectors)
Decision: `diff_repair::validate_and_repair` runs three normalisation passes IN ORDER, then the four fatal-failure detectors against the NORMALISED body. (1) `normalize_line_endings(text)` strips a leading UTF-8 BOM (`\u{FEFF}`) and unifies CRLF/CR → LF. (2) `align_to_original(normalised, original)` swaps LF → CRLF when the original used CRLF, AND mirrors the original's trailing-newline state (drop or re-add a single trailing newline to match). (3) Detectors run against the post-normalisation body — truncation byte ratio, full-rewrite line-disjoint check, ChatML body-marker scan (excluding the trailing 16 bytes). The PartialChatMLEmission detector runs BEFORE normalisation so the marker isn't accidentally smoothed away by line-ending fixes; everything else runs AFTER.
Reason:   This is the order that respects "fix the drift the model made; reject the structural failures the model can't fix". CRLF / trailing-newline drift is the most common Kortix-7B failure on Windows-CRLF source files (per S25's documented 30% apply-fail rate). Normalising BEFORE detection means truncation (a byte-count threshold) judges the post-cleaned size, not the pre-cleaned size — which would flag legitimate edits that just dropped a trailing newline. The PartialChatMLEmission scan runs first because line-ending normalisation can split a marker if the model emitted `<|im_end|\r\n>` mid-stream — checking before the replace preserves the marker for detection. The 16-byte trailing exclusion mirrors S25's `strip_chatml_trailer` window so the two layers don't double-count the same end-of-stream marker.
Impact:   `desktop/src-tauri/src/ai/diff_repair.rs::validate_and_repair` is the SSOT for the normalisation order. Future sessions adding a new normalisation pass (e.g. tab-to-spaces conversion) MUST land it BEFORE the detectors, AFTER `align_to_original`. The order is locked by 7 unit tests in the module (`normalize_unifies_crlf_lf_mixed`, `normalize_strips_bom`, `normalize_handles_lone_cr`, `align_swaps_lf_to_crlf_when_original_was_crlf`, `align_reattaches_trailing_newline_when_dropped`, `align_strips_extra_trailing_newline`, `validate_and_repair_normalises_crlf_drift`) plus the integration test `apply_v2_normalises_crlf_drift_and_serves_local`.

## 2026-05-01 — Sesión 26 (retry policy: MAX_LOCAL_ATTEMPTS = 2, repair prompt augments instruction inside `build_fast_apply_prompt` envelope, NEVER mutates v1 prompt format)
Decision: The Fast Apply local path attempts up to 2 generations before falling back to cloud. Attempt 1 uses `build_fast_apply_prompt(target_body, &instruction)` (the S25 v1 format, locked by 3 unit tests). Attempt 2 uses `build_kortix_repair_prompt(&instruction, target_body, &error)` which AUGMENTS the user instruction with an `IMPORTANT: <guidance>` footer — but stays inside the same `<|im_start|>system / <|im_start|>user / <|im_start|>assistant` ChatML envelope and the same `<code>` / `<update>` tag pair. The `target_body` argument is the ORIGINAL source on attempt 2 (NOT the model's failed output) — re-feeding the broken output as `<code>` would prime the model to repeat its mistake. The base instruction is built ONCE and passed by reference to both prompt builders so the natural-language description of the fix is identical across attempts.
Reason:   `MAX_LOCAL_ATTEMPTS = 2` is the right ceiling for two reasons. (a) The Q4_K_M Kortix-7B inference takes ~2-3 minutes for a 4096-token completion on a Tier2 box; two attempts caps the wall-clock budget at ~6 minutes, which is the ceiling the dock's "Inari is fixing this…" affordance can absorb without losing the user's attention. (b) The S25 spec documented ~30% local-apply failure on first try, and the recoverable failure modes (PartialChatMLEmission + EmptyOutput) are transient tokeniser-level glitches that resolve on the second sample — three attempts would not meaningfully improve the success rate over two but would double the cost in the failure case. The "augment, don't mutate" v1-prompt rule is locked because S25's DECISIONS entry explicitly forbids silent v1-prompt mutation: "If S26 wants to A/B test prompt variants, the right move is to introduce a `build_fast_apply_prompt_v2` peer + a config knob — never silently mutate the v1 wording (the test fixtures lock it)." `build_kortix_repair_prompt` honours this by being a peer that DELEGATES to `build_fast_apply_prompt` after augmenting the instruction.
Impact:   `desktop/src-tauri/src/ai/remediate/single_shot.rs::MAX_LOCAL_ATTEMPTS = 2` is the SSOT. The 5 named integration tests + sweep all exercise this exact attempt count — `apply_v2_retries_on_parse_fail` asserts `KORTIX_CALLS == 2` after success, `apply_v2_falls_back_to_cloud_after_2_retries` asserts `KORTIX_CALLS == 2` before cloud fallback, `apply_v2_detects_truncation` + `apply_v2_detects_full_rewrite` (no-intent) both assert `KORTIX_CALLS == 1` (fatal classifiers skip the retry). Bumping MAX_LOCAL_ATTEMPTS to 3 must extend the affordance budget AND update all 4 counter assertions.

## 2026-05-01 — Sesión 26 (git_apply_check is best-effort: skip when repo isn't git-backed; orchestrator's apply_diff is the real gate)
Decision: `single_shot::git_apply_check(repo_path, diff)` returns `true` when `repo_path/.git` does not exist — i.e., when the repo isn't a git checkout. When the repo IS git-backed, it writes the diff to a uuid-suffixed tempfile, runs `git apply --check <patch>` from `repo_path`, removes the tempfile, and returns the exit-status outcome. The function is INSIDE the local Kortix retry loop — a clean apply check on attempt N short-circuits the loop with `Some(draft)`; a failed check (when git-backed) is treated as the same "recoverable" class as PartialChatMLEmission (retry with repair prompt or escalate to cloud after MAX_LOCAL_ATTEMPTS).
Reason:   Two motivations. (a) The dock's `apply_diff` (orchestrator) ALREADY runs `git apply --check` before applying — that's the production gate, and it's strict (fails the whole remediation if the diff doesn't apply). The S26 in-loop check is an EARLY filter that lets the retry loop discriminate "model produced an apply-clean diff" vs "model produced a structurally-valid but on-disk-incompatible diff" within the local retry budget. (b) Some test fixtures (e.g. `fast_apply_local_zero_cost.rs`) intentionally don't `git init` — they only verify the cost contract, not the apply contract. Failing the in-loop check on a non-git repo would force every test to set up a real git checkout; making the check best-effort lets those tests stay focused on what they actually verify, while real-world usage (where the user always has a git repo) still gets the early filter benefit. The orchestrator's `apply_diff` is the SSOT for "this diff actually applies" — the S26 check is an optimisation, not a security gate.
Impact:   `desktop/src-tauri/src/ai/remediate/single_shot.rs::git_apply_check` is the helper. The legacy `fast_apply_local_zero_cost.rs` test continues to pass (no `.git` → check skipped → original cost-ledger semantics preserved). The new `apply_v2_normalizes_crlf.rs` and `apply_v2_retries_on_parse_fail.rs` tests `git init` their tempdirs explicitly so the in-loop check fires and proves the CRLF-aligned diff applies cleanly. Impact:   `desktop/src/components/ui/EmptyState.tsx` is the canonical primitive. Re-exported through `components/ui/index.ts`. The 4 main shells (`Inbox.tsx`, `Activity.tsx`, `Memory.tsx`, `Patterns.tsx`) are rewritten to use TopBar + EmptyState instead of bare placeholder text — they ship as polished empty states until Sesión 19 wires real data. Future "search returned 0 results" / "no history yet" / "no team members invited" surfaces MUST use this primitive; introducing a competing empty-state shape requires a DECISIONS entry.

## 2026-05-01 — Sesión 33 (TopBar primitive: 56px tall, 18px title peso 600 left-aligned, 28×28 ActionSquare for right-rail icons)
Decision: A new `TopBar` primitive (`desktop/src/components/ui/TopBar.tsx`) is the canonical screen header. Anatomy: 56px tall (h-14), `--bg` background, `--border-subtle` bottom border (NOT a heavy `--border`), 24px horizontal padding. Three slots: `title` (18px peso 600 in `--text`, left-aligned, truncates), optional `meta` (12px in `--text-muted` directly under the title — counts, breadcrumbs), optional `actions` (right-aligned row of 28×28 `ActionSquare` icon buttons). `ActionSquare` is a paired primitive: 28×28 hover bg `--card` square with focus ring, used for filter / search / display options / kebab buttons across the app. Adopted by all 4 main shells (Inbox/Activity/Memory/Patterns) in S33; future screens MUST use it instead of hand-rolling header markup.
Reason:   The 9 Linear screenshots show a consistent top-bar pattern — page title left-aligned at 18-24px, 28×28 action squares right-aligned with hover bg, no shadow, no gradient bg, only an ultra-subtle bottom border. The pre-S33 main shells used `<h1 className="font-[var(--font-serif)] text-2xl mb-2">` inline + no actions row — visually disconnected from the rest of the product. A single TopBar primitive locks the shape so screens can compose it as `<TopBar title="Inbox" actions={<ActionSquare ariaLabel="Filter">...</ActionSquare>} />` without re-deriving heights, padding, border colors per shell.
Impact:   `desktop/src/components/ui/TopBar.tsx` is the SSOT. Re-exported through `components/ui/index.ts`. `MainInbox`, `MainActivity`, `MainMemory`, `MainPatterns` all consume it. Future screens (alerts list, alert detail, on-call, etc.) MUST use it. The `ActionSquare` primitive is the canonical 28×28 hover button — it's reused inside the Sidebar header (search, compose) AND inside TopBar action rows, so future sessions adding a new icon-only button reach into it instead of a bespoke implementation.
